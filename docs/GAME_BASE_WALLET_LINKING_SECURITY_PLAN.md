## Proposed protocol (requires separate implementation and review)
1. Isolate a wallet-link service from gameplay and swap execution. Exact official HTTPS origins, POST JSON, bounded size/time, no credential logs, no cache, rate limits by verified account and address. Server obtains current registered Supabase UID using authoritative user validation; never trust client UID or localStorage. Preserve email/social login, guest mode and hero save keys.
2. Challenge request accepts a canonical nonzero EVM address and supported chain 8453 only. Require explicit consent, fresh authenticated registered account and server-issued challenge ID with >=128 random bits, short expiry (at most five minutes), one pending challenge per account/address policy. Reject anonymous sessions. Bind exact UID server-side, purpose "Climboria game wallet ownership linking", origin/domain, URI, chain ID, address, nonce, issued-at and expiry. Use a standard SIWE/EIP-4361 message and reviewed maintained verification library, not homemade secp256k1 or a raw arbitrary hash. Do not expose the private Supabase UID in public on-chain data or logs; an opaque challenge ID binds it in storage. No arbitrary user message, typed-data spending permission or transaction.
3. Client displays exact address, network and message, explains off-chain ownership signature only (no gas/approval/transfer), checks account and chain immediately before requesting personal_sign and invalidates pending UI on account/chain/auth changes. Do not prompt until the actual verified backend is deployed and accepted. Connection alone never marks linked.
4. Verify against the exact stored message and challenge with fresh server-validated same registered UID; server checks nonce, purpose, domain, chain, expiry, address and signature. Initial proposed scope is EOA key proof only; contract-wallet/EIP-1271 and delegated EIP-7702 semantics require distinct reviewed verification with explicit network/code provenance. Do not mislabel key recovery as current smart-wallet controller proof. Fail closed on uncertain chain evidence or unavailable verification. No client-supplied verified flag.
5. Atomically consume challenge and insert verified wallet association in one durable transaction. Unique active (chain,address) across accounts, exact account ownership and immutable evidence ID; never silently move an address between accounts or switch login UID. Handle duplicate/retry idempotently for same account without a second association. Conflict returns generic failure without revealing the other account. Invalidate outstanding challenges on unlink/epoch change. Only one authoritative database; no browser/KV-only nonce state. Direct browser write to verified associations forbidden by database permissions/RLS. No automatic cross-account recovery or merge.
6. Store minimal evidence (chain, canonical address, account reference, challenge digest/ID, verified time, method/version, revoked status); no private keys, bearer tokens or raw signatures in logs. Define retention, user-visible history and revocation. Revalidate before any future reward reservation; freeze payout recipient per approved economic event. Unlink/relink cannot change already-reserved recipient or create duplicate rewards. Account recovery and wallet conflicts require deliberate separately reviewed policy.

## Acceptance matrix before any real signature
| Boundary | Required negative and positive tests |
| --- | --- |
| Registered identity | signed-out, expired, anonymous, wrong UID, unavailable auth service, valid registered account; no account switching |
| Challenge integrity | wrong origin/domain/purpose/chain/address/nonce/message/expiry; malformed/oversized inputs; signature mismatch; canonical address case and zero address; at least 128-bit randomness |
| Wallet proof | independent known EIP-191/SIWE vectors; wrong signer; malleability/encoding policy; contract/delegated wallet unsupported or separately reviewed; chain evidence failure |
| Durable state | concurrency across instances, duplicate use, rollback after insert failure, same-account retry, cross-account conflict, restart, stale epoch/revoke, unauthorized direct writes, no replay after unlink |
| Browser | explicit consent, no automatic prompt, wrong chain, account change during signature, reject/cancel, auth switch mid-request, no token approval or network switch; desktop and mobile wallet browsers |
| Operations | origin, rate/size/time limits, sanitized errors and logs, service key isolation, database RLS, reviewed deployment config and rollback, no real funds |
