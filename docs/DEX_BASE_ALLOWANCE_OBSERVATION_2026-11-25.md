## 2026-11-25 follow-up — EIP-1898 hash-bound Base state reads (pending exact-head CI)

- Branch `dex/base-allowance-eip1898-hash-pinned-20261125` starts from main `0d66fb3878387b7bb9ec731147e09ccf596a83bb` after #756. The prior same-height before/after hash fence only compared the identity of the numbered block at two instants: it did not *cryptographically address* each intermediate `eth_getCode` / `eth_call`, so an in-between reorg or untrusted endpoint could serve reads from a different block at the same height.
- This branch upgrades both holder and ERC-20 `eth_getCode` and exact `balanceOf` / `allowance(owner,holder)` `eth_call` requests to EIP-1898 block selectors `{blockHash: initialBlockHash, requireCanonical: true}` instead of the block number string. The original `eth_chainId=0x2105` before/after, runtime SHA-256 check, token runtime presence, strict uint256 decoding and post-read block hash check remain. An RPC that does not support hash-pinned reads, returns an error or reports the block as noncanonical must FAIL CLOSED; **no fallback** to number-based observations. The returned allowance decision remains read-only, `executable:false` and never returns transaction data.
- Offline regression now checks exact EIP-1898 parameters and rejected unsupported RPC method with no retries; live read-only Base RPC smoke checks both token directions with the same hash for all four state reads.
- **Pending verification at creation:** EIP-1898 support and live result on public `https://mainnet.base.org` are *not assumed*. A green static test does not establish compatibility. If the real public RPC rejects the hash form, do not merge an unverified change as though observations still work; diagnose and implement a separately reviewed provider-supported consistency alternative or retain the prior fail-closed hash-before/after baseline.
- **Security limitation:** EIP-1898 ensures state addressing by block hash only to the extent the RPC truthfully implements it. A single public endpoint is not independent cryptographic provenance/finality, ERC-20 proxy/implementation attestation, current route/settler semantics or approval/transaction permission.
