## Proposed minimum semantic changes, subject to explicit approval
Use per-recipient context monotonicity, not global epoch changes on failed/cancelled nomination. One possible compact representation is a uint256 context per address, even=eligible context, odd=blocked pending release, initial zero. On successful nomination increment to the next odd value (even+1 or odd+2). On explicitly authorized release increment odd to even only when current role eligibility and no live nomination allow it. Arithmetic checked; no wrapping. This representation is proposed, not selected or compiled. A successful actual swap retains global epoch invalidation and owner exclusion. Former owner eligibility remains a separate owner decision. For a formerly nominated owner later rotated out, explicit release is still required if context remains odd. Ordinary current role and beneficial-owner screening are separate.
1. Add a virtual internal nomination hook to the base guard after validated pending state is written; reserve override updates recipient context atomically; base rotation-only fixture stays behaviorally unchanged. No updates on failed schedules. Avoid external callback and unbounded loops. Same-address renomination must invalidate prior contexts even if still blocked; unrelated recipients unchanged.
2. Add typed quorum-only release call bound to current epoch, exact recipient and expected blocked context plus existing signed window, e.g. releaseExpenseRecipient(uint256,address,uint256,uint256,uint256) (164 bytes). Require exact selector/length whitelist only after binding, current config, no live pending nomination, and ordinary role eligibility; separate underlying role predicate from context eligibility to avoid self-deadlock. Release does not transfer funds and cannot re-arm a prior proposal.
3. Add one explicit expected recipient context to proposeExpense (10 static args, 324 bytes); remove old 292-byte selector from allowed calls. Require matching current even context. Bind context in vault propose parameters and proposal ID; persist in proposal struct or separate per-proposal mapping, with exact ABI/storage tradeoff evaluated before selection. Execute checks stored context equals current even context before spend/evidence changes. Do not rewrite or mark executed old proposals. Evidence remains reusable if no actual consumption.
4. Extend dedicated expense custody interface, not unrelated reward/liquidity interface unless required. No permissive default for missing context getter. Existing mock adapters intentionally unrestricted for earlier test suites must explicitly supply test contexts. Known exact source consumers: V3AtomicSuccessor.t.sol SuccessorMockCustody; V3EpochPolicy.t.sol MockEpochCustody; inherited V3SecurityFuzz.t.sol; V3SecurityInvariant.t.sol direct propose call. Full call-site inventory must be completed at implementation, including older fixtures that use separate V3SharedRestrictedSpend API (do not accidentally change those).
5. Update canonical envelope allowlist, typed intent selector/length and ID derivation, receipt expectations, local authorization and expense execution rehearsal, and every affected test. If Proposal getter layout changes, require exact new tuple decoding; never accept old and new schemas under same release identity. Rebuild review packet, artifacts and negative vectors. Existing authorization evidence is historical, not a substitute for new implementation tests.
