# V3 game reward authorization service — production gate

2026-11-27 UTC. Test-only settlement implementation exists in PR #866. No game reward program or payout is live. This is a review draft, not an approved reward rate, schedule or production API.

## Trust boundary

The client may request a reward status but may not submit a self-attested score, chest, combat outcome or amount for signing. The authoritative game service must establish an eligible finalized event from trusted server state, authenticate the account and prove control of the linked Base payout address. Current per-client chest timers and approximate multiplayer movement are not financial event evidence. Do not authorize payouts from those sources. No production key in the browser or repository.

Canonical event identity must be derived from versioned, immutable server-side evidence (program, game event namespace, authoritative event ID, finalized adjudication), not a random ID supplied by a client or independently regenerated by each worker. Use a unique durable database constraint per program/event; corrections and disputes must not create a second payable ID for the same economic entitlement. Deduplicate across workers, retries, key rotation and successor deployments. Keep personal account data off chain.

## Required settlement flow

1. Finalize eligible event server-side; validate published program rules, account standing, anti-cheat, ownership proof, amount and funding. Lock an immutable recipient and approved raw amount.
2. Atomically reserve the event ID and amount against current global, program and account budgets. Use integer units, not floating point. A wallet ceiling is only a secondary limit, not a person or Sybil limit.
3. Construct the exact EIP-712 reward for the reviewed deployed vault, chain, current model month and short deadline. Signing service must authenticate the authoritative request and enforce its own policy. Production signer custody, rotation and emergency revocation are unresolved; fixed fixture signer is not acceptable as-is.
4. Return only the signed authorization; it can be relayed by anyone but cannot redirect the recipient. No claim of payment until finalized receipt, exact RewardPaid event, token transfer, chain/vault and accounting reconciliation. Retry the same event identity; do not create a new payable event because a submission timed out.
5. If expired/unsubmitted, verify finalized paid state and all outstanding authorizations before allowing reauthorization of the same event/recipient under reviewed rules. Across deployments, a shared authoritative ledger and reviewed on-chain migration boundary must prevent duplicates.
6. Track awarded, reserved, signed, submitted, finalized, expired and disputed separately. Reorgs, uncertain receipt, database failures and signer outages must fail closed; reconcile before retry. No promise of rewards or automatic payment based on a client score.

## Acceptance gates

- Real authoritative game-event integrity and independently reproducible eligibility; no client spoofing, duplicate events, account takeover, wallet substitution or fake rewards.
- Durable concurrent reservation and idempotency tests across process restarts; explicit late-finality and reorg recovery.
- Production custody dependency review, signer rotation/revocation, account-level anti-Sybil limits, reviewed reward terms and funded allocation.
- Exact on-chain domain, expiry, caps, event ID replay, recipient and transfer accounting; verify finality independently.
- No live reward feature flags or public reward commitment until the above evidence passes. The fixture does not prove any real player's eligibility.
